# Accepted delivery contract

Accepted by the owner on 2026-09-07 when activating the long-running Descenders delivery goal. These defaults and public TDD seams are approved, subject to later recorded decisions in ADRs and the delivery ledger. This is an acceptance contract, not evidence of implementation. Epic #121 (closed 2026-09-11) and milestone 7 tracked completion; open work is on map #143. Production release, paid resources, real invitations and external athlete-data transfer require separate authorization.

**Approved product defaults**

| Area                 | Approved first-release behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Club model           | Default to one club per installation. Model user-to-club membership explicitly, so an operator can bootstrap another club and appoint its admin. No public club signup, billing, custom domains or elaborate tenant provisioning.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Access               | Members read their club's private squad/editorial context and the authenticated league result context already permitted by the map. Coaches manage assigned squads and draft stories. Club admins manage that club's memberships, invitations, squads and publication. Operator provisioning is a separate bootstrap command. No role grants power over another club.                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Personal squad       | Save a preferred squad per user, club and season. With one assigned squad, select it automatically. With several, offer a choice. With none, show the season plus an honest unassigned state and available club squads. A preferred squad is a navigation preference, not permission.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Club member audience | Invite-only club accounts, initially adults/coaches. Family-account relationships and independent minor-account onboarding remain outside this release unless separately specified.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Squad ownership      | The database becomes authoritative after bootstrap. Coaches may create/manage squads they own or are assigned; club admins manage all club squads. Multiple squads per rider are valid. Membership requires that season's club roster.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Squad lifecycle      | Archive instead of deleting historical identifiers. Keep archived links understandable, reserve slugs within the club/season, and do not fabricate historical membership. Use neutral, short squad names with guidance against judgments about children. No athlete notes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Invitations          | Club-scoped role and optional squad assignment, verified invited email, hashed high-entropy token, expiry, single-use acceptance, revocation and minimal actor/time audit. Acceptance is transactional. Amended by the owner 2026-09-11 (#128): the invite is a magic link. Club admins invite. So does any member an admin grants the per-club "can invite users" permission. Only club admins grant or remove it, and a holder cannot pass it on. Holders invite members and coaches; only club admins invite or promote admins. An email with an active club membership is refused, and a new invitation replaces a pending one. Acceptance may reactivate a revoked membership (ADR-0007). Membership revocation takes effect on the next protected request. Protect the last active admin from accidental removal. |
| Editorial            | A small structured draft with evidence references and a club-admin publish action. Approved narratives are explicitly allowed through a narrow successor to ADR-0003. Keep private observations, behavioral assessments and athlete discussion logs outside the model.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Story behavior       | Manual story selection for release one. Automatic rotation remains an experiment. A page without an approved narrative still has factual counts, chart labels and a useful question; it must not fabricate a story.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Hosting              | Implement against standard Postgres with Neon/Vercel as the initial deployment candidate. Choose the driver and runtime after checking current primary documentation. Do not make PGlite persist on an ephemeral hosted filesystem.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

The role and membership model must distinguish published league results from club-private configuration. The map explicitly permits named league-wide results behind auth. That does not grant permission to inspect another club's invitations, preferences, unpublished drafts or administrative data. Scope every private read and mutation on the server, including direct URLs and actions. Resolve squad URLs within club context so identical slugs in two clubs work.

ADR-0005 narrowly supersedes ADR-0003’s historical plate-attachment-only boundary. Management and reviewed editorial writes follow that accepted replacement. Preserve the description/adjudication boundary and the existing protection of athlete data. The repo is currently MIT-licensed. This plan interprets “public domain” as publicly reusable source and leaves the license unchanged pending an explicit licensing decision.

**Approved public TDD seams**

The owner explicitly approved the following public seams. Record each behavior and its red/green evidence; request clarification only for a genuinely new public boundary.

| Public seam                                    | Behaviors to prove                                                                                                                                                                                                                                                          |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Protected request/action boundary              | Anonymous denial; member/coach/admin permissions; direct URL and forged-ID checks; cross-club private data isolation; revoked access; invite expiry/replay/wrong-email rejection; safe last-admin behavior.                                                                 |
| Reporting query functions over migrated PGlite | Correct category/conference denominators; checkpoint excludes later races; one-finisher fields; DNF and lap deficit; current names; missing results; category changes; membership deduplication. Use existing integration helpers and independently worked expected values. |
| Management commands/actions                    | Permitted squad membership changes, multiple membership, archive behavior, stable links, preferred-squad fallback, bootstrap idempotency and reseed preservation. Observe through public reads.                                                                             |
| Editorial draft/publish boundary               | Every reference exists and supports the claim; out-of-checkpoint evidence rejected; only permitted roles publish; source correction makes stale publication visible or withdraws it.                                                                                        |
| Components and browser journeys                | Accessible chart meaning and values, perspective switch, keyboard controls, navigation context, invitation → login → season/squad/rider, and admin management flows. Assert behavior rather than markup snapshots.                                                          |
| Database adapter/migration boundary            | Same public repository behavior on PGlite and disposable Postgres; transactions, fresh install and upgrade from existing schema preserve data.                                                                                                                              |

For each behavior: write one failing test, run it and confirm the intended failure, implement enough to pass, then move to the next behavior. Keep each slice working end to end. Refactoring belongs in the subsequent review pass. Runtime-validate external inputs, keep domain types explicit, use parameterized database operations, and avoid `any` or non-null assertions that conceal missing states. Reuse existing modules before introducing abstractions.

Public CI gets synthetic fixtures. The existing local corpus lane stays local. Do not refetch the league corpus already present. New tests should observe public behavior rather than private collaborators. Update the agreed seam list when a genuinely new public boundary becomes necessary.

**Completion evidence**

The final acceptance ledger must connect every row below to a command result, browser observation, test or review artifact, with the commit and date. Separate passed, failed, not run and externally blocked.

- A documented fresh-start procedure installs dependencies, migrates, seeds a safe demo and starts the local app. Persistent PGlite retains preferences and squad changes after restart. Existing local data is backed up before upgrade checks.
- Local login works, and production-mode magic-link behavior is exercised with a local test mailbox using synthetic accounts. The development login cannot activate in production. New, expired, reused and revoked invitations behave correctly.
- The current configured season appears after login, with the saved squad or an explicit fallback. Current-season data is distinct from the 2025 validation corpus. Missing current data does not silently become last season's data.
- Member and admin browser journeys reach the season, other allowed squads, race review, athlete season and athlete race detail through links and direct URLs. Back navigation preserves context.
- All reporting pages satisfy the visual/editorial table. No placeholder chart geometry, invented membership or synthetic values leak into real-data views. Race 2/3 evidence respects its checkpoint.
- Public tests, authorized local corpus tests, typecheck, lint, formatting, privacy checks, migration checks and production build pass. Run brand comparison per repo guidance, recording a skipped check honestly. Add a production build and critical synthetic browser journey to CI.
- A disposable Postgres instance proves the selected hosted driver and migrations. Build/start uses production settings with no dependence on local PGlite persistence. Authentication, commands and reporting share a safe connection strategy.
- The runbook covers environment variables without secrets, initial admin/club bootstrap, persistent local storage, hosted runtime/driver setup, connection limits, migration ordering, backup/restore, source ingestion and corrections, and rollback-compatible release steps. Reproduce it with synthetic data.

Neon and Vercel account creation, billable resources, real recipient emails, external transfer of athlete data and production deployment are not implied by approval of a deployment-ready build. Prepare the code and commands first. If provider credentials are unavailable, complete local Postgres and production-mode checks and label provider preview verification outstanding. Do not claim a verified hosted deployment. A user-required hosted acceptance check keeps the delivery goal incomplete until that check can run.
